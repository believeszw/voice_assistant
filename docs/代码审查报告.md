## 2. 架构与分层

依赖方向是干净的、单向的（没有循环导入）：

```
assistant.py  ──► frontend.py ──► aec3.py / aec_nlms.py
     │              └──► config.py
     ├──► audio.py（麦克风/VAD/录音）
     ├──► asr.py（Vosk）/ asr_local.py（sherpa 双遍）/ llm.py（云端）
     ├──► intents.py（规则）/ nlu_local.py（端侧 LLM）
     ├──► tts.py ──► tts_local.py（Piper/VITS）/ llm.py
     ├──► actions.py ──► config.py
     └──► kws.py / hotkey.py
```

做得好的地方：

1. **一个模块一件事**：`audio`（采集）、`frontend`（AEC/VAD/NS/AGC/打断）、`intents`（规则）、`llm`（云 API）、`actions`（系统动作）边界清楚，替换其中一个不影响其他。
2. **降级链完整且显式**：识别（端侧双遍 → 云端 → Vosk）、播报（云端 → Piper → VITS → SAPI）、AEC（AEC3 → 自研 FLMS）；每条降级都有日志和回退条件。
3. **失败可解释**：`[动作] xxx -> 结果`、`[状态] IDLE -> SPEAKING`、`[打断] …（rms/ratio/base/prob）` 这些日志让排障成本很低。
4. **安全意识到位**：`actions._SAFE_TARGET` 白名单、危险动作二次确认、`far_sink` 参考信号隔离。

主要结构性问题：

- `Assistant`（862 行、27 个方法）同时承担：状态机、对话循环、ASR 策略、打断确认、播报编排、环境打印。它是"上帝对象"。
- `intents.parse` 是一个 177 行的顺序 `if` 链，规则之间**存在隐式优先级**（如「取消关机」必须在「退出」前、「静音」必须在「音量」前），加规则容易踩顺序坑。
- 三条 TTS 后端（云端/Piper/VITS/SAPI）× Speaker 线程模型，状态（`_playing/_pause/_stop/_busy`）分散在多个方法里，是最容易出并发 bug 的地方。
